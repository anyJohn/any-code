# 代码审查

被要求审查代码（"review 一下"、"看看这个改动有没有问题"）时，按本清单系统执行，不要凭印象泛泛而谈。

## 流程

1. **先读后评**：完整读改动（diff 或文件），再看被改函数的调用方与被调方——脱离上下文的审查会产出错误建议。
2. **跑一遍**：能运行的改动先跑测试/构建，用事实说话。
3. **按五维过清单**，每条发现给出：位置（file:line）+ 问题 + 建议修法。

## 五维清单

- **正确性**：边界条件（空/零/负/超界）、错误路径是否处理、off-by-one、null/undefined、返回值约定一致
- **安全**：注入（命令/SQL/路径拼接）、敏感信息硬编码、权限校验缺失、不可信输入直接进 eval/exec
- **并发与资源**：竞态、未释放资源（句柄/连接/子进程）、abort/超时是否传播、错误吞掉不报
- **可读性**：命名表意、函数过长（>50 行警惕）、重复逻辑、魔法数字、注释与代码不符
- **测试**：改动是否有对应测试、是否只测 happy path、断言是否真的验证行为

## 输出格式

按严重级别分组，每组内按文件组织：

- **阻塞**：不改就不能合（正确性错误 / 安全漏洞 / 破坏现有行为）
- **建议**：应该改但有绕行方案（性能 / 健壮性 / API 设计）
- **nit**：可选（命名 / 风格 / 注释）

没有发现的维度也要说明"已检查无问题"——沉默会让人怀疑你没看。

## 原则

- 对事不对人；每条建议给理由，不给"我觉得"。
- 区分"事实问题"与"口味差异"——口味差异标注为 nit 且不坚持。
- 审查的是代码，不是人；发现系统性问题（同类错误多处出现）单独指出模式。
