# 发布检查单

被要求"发个版本 / 发布一下"时，按序执行，**每步完成再进下一步**，不跳步。

## 1. 定版本（semver）

- 有破坏性变更（API 删除/语义变化/配置不兼容）→ **主版本 +1**
- 新增功能且向后兼容 → **次版本 +1**
- 只有修复 → **修订号 +1**
- 不确定是否破坏性 → 先列出公开接口/配置的变更让用户确认，别自己拍

## 2. 变更清单（changelog）

从提交历史/需求单整理，按"新增 / 变更 / 修复 / 移除"分组，面向用户措辞（写行为，不写实现细节）。不确定的条目找用户核对。

## 3. 发布前检查

- [ ] 全量测试通过（不是只跑改动相关的）
- [ ] 全量构建通过（产物存在且可启动）
- [ ] 版本号已在版本载体更新（package.json / 版本文件）
- [ ] 文档与新版本一致（README / changelog / 配置说明）
- [ ] 干净环境从产物走一遍快速冒烟（启动 → 核心功能一条 → 退出）

## 4. 提交与打标

- 发布提交单独、干净（不含无关改动）；tag 指向发布提交
- tag 名与版本号完全一致（如 `v1.2.3`）

## 5. 发布

- 按项目既定通道发布（CI tag 触发 / 手动上传产物）
- 产物完整性：能下载、能安装/解压、能启动

## 6. 发布后

- [ ] 线上/安装版冒烟一条核心路径
- [ ] 回滚预案可用（上一版本产物在手，知道怎么切回）
- [ ] 公告/通知（如有）

## 原则

- 发布中发现新问题：**停下来评估**——修了重走检查单，或带已知问题发布并明确记录，二选一，不静默带过。
- 用户数据与配置的安全优先于发布进度。
