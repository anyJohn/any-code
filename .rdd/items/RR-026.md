# RR: 工具权限系统（allow / ask / deny + 危险命令确认）

## 需求来源与背景

- `docs/架构和功能改进需求.md` AR-3（P0 唯一安全需求）：工具执行前策略判定，allow/ask/deny 有序规则集，deny 最高优先，审计可回放，三种预设模式。
- 业界核查（summary.md / 架构和功能改进需求.md）：6 个开源 agent 中 5 个有权限/审批门控（allow/ask/deny 或审批 waterfall），唯一没有的项目把隔离外包给容器沙箱。权限系统是 P0 共识安全债。
- 现状代码：`toolCall.ts` 在 handler 执行前后已发 ToolStart/Tool 事件并自留"未来权限拦截点"注释；`prompt.ts` 已向 LLM 声明"危险命令由 permission 层处理"——该层不存在。
- 沙箱核查结论（AR-5 调降 P2）：第一道安全门是权限系统，不是沙箱。

## 业务目标

让"agent 在用户本机执行任意命令/改任意文件"从裸奔变为有门控：危险操作执行前经策略判定，`ask` 弹 UI 请用户裁决（允许一次/永久允许/拒绝），`deny` 任何模式下硬拦；裁决持久化为规则，越用越顺；全过程产生审计事件可回放。

## 范围

- 纳入：内置工具（bash / write / edit 为主，只读工具默认放行）与 MCP 工具；规则引擎；预设模式；ask 交互与裁决持久化；审计事件。
- 不纳入（后续需求）：沙箱/执行环境抽象（AR-5，P2）、工具元数据模型（AR-7，P1，届时权限默认值由元数据推导）、TUI 桌面端完整 ask 体验（首版降级，见 FE open questions）。

## 场景与流程

- 场景 A（增量改进）：既有调用方（agentLoop → toolCall → handler）不变，在 toolCall 分发前插入策略判定 seam。既有 SPEC-022（工具系统）仍适用，本需求新增 SPEC。
- 影响面：domain（toolCall / 新权限模块 / config / 事件类型）、server（无新路由——复用 /interact 通道）、web（ask 交互 UI）。

## 未确定事项（blocking，见 FE-023）

1. 出厂默认模式（放行/询问的边界画在哪）
2. 规则匹配粒度（工具名级 vs 工具名+参数模式）
3. 裁决持久化位置（项目级 / 全局 / 两级）
4. 首版 ask 交互端覆盖（web 先行 vs 三端同步）

## 决策（Human 已确认，2026-09-01，冻结）

| # | 决策 | 值 |
|---|---|---|
| D-1 | 出厂默认模式 | 命令+写入询问：bash/write/edit ask，只读工具放行（Claude Code 式） |
| D-2 | 规则匹配粒度 | 工具名+参数模式：bash 命令 glob/前缀、文件路径 glob（opencode/Claude Code 同构） |
| D-3 | 裁决持久化 | 两级可写：永久允许/拒绝默认写项目级，弹窗可勾"全局"；项目级评估在全局之后（后匹配覆盖） |
| D-4 | 首版交互端 | web 先行做完整裁决 UI；TUI/桌面复用现有 Interaction 降级路径（超时按拒绝，与 ask_question 一致） |
