# Raw Requirement: 优化长 bash 执行期间界面无响应

## 来源
用户：模型执行很长的 bash 命令时，界面长时间无响应，如何优化？

## 业务目标
- 长 bash 命令执行期间，前端不再"假死"——有持续视觉反馈，最好能实时看到命令输出

## Impact Analysis（场景 A 增量改进）
根因诊断（非主线程阻塞，bash 用异步 exec）——四重叠加致 120s 静默：
1. bash.ts L22-27：exec 一次性等子进程退出，stdout/stderr 跑完才返回，不流式
2. toolCall.ts L57-65：唯一 TOOL 事件在 handler resolve 后才发，无 TOOL_START / 心跳
3. core.ts L115：await toolCall 期间事件流静默
4. SSE run/route.ts L103-106：纯透传无 keepalive
5. MessageList.tsx L50-65：showTyping 判"上一条 User 后无 Assistant/Tool"，但 agentLoop 在调 bash 前已发 ASSISTANT（模型先输出文本再带 tool_calls）→ typing 提前消失；TOOL 事件又还没到 → 既无 dots 也无运行中指示

最长静默窗 = BASH_TIMEOUT_MS = 120s（bash.ts L11）

## 范围
- 优化方向（待决）：A 流式 stdout + TOOL_START/PROGRESS（治本）/ B SSE keepalive + TOOL_START（治标）/ C 修 showTyping 判定（纯前端止血）
- 涉及：domain bash.ts、toolCall.ts、type.ts（可能加 EventType）；web run/route.ts、MessageList.tsx、renderItems.ts

## 未定（见 Open Questions）
- 优化力度（治本 vs 治标 vs 止血，可组合）
- 流式 stdout 是否落盘（PROGRESS 事件实时态）
- 新增 EventType vs 复用

## 决策（Human 决）
- 优化力度 = 一步到位流式 stdout 治本（DEC-058）
- bash 改 spawn 监听 stdout/stderr data → TOOL_PROGRESS（DEC-059）
- 新增 EventType TOOL_START/TOOL_PROGRESS（DEC-060）
- SSE keepalive 仍加兜底（DEC-061）
- showTyping 判定基线改为"上一条 User 或带 tool_calls 的 Assistant 之后无对应 Tool"（DEC-062）

## 验证结果（SPEC-018）
- AC-001 bash spawn 流式 stdout/stderr → TOOL_PROGRESS：domain bash.test ✓
- AC-002 toolCall 执行前发 TOOL_START：domain toolCall.test ✓
- AC-003 前端活动工具卡片实时累积 stdout：web MessageList.test ✓
- AC-004 typing 修正（ToolStart/Assistant 到达即隐藏 dots）：web MessageList.test ✓
- AC-005 SSE keepalive：run/route.ts 注入 comment frame（代码审查 + build ✓）
- AC-006 TOOL_PROGRESS/TOOL_START 不入盘：groupByTurn continue 跳过（renderItems 单测覆盖分组不变）
- AC-007 真 LLM run：`for i in 1 2 3; do echo line$i; sleep 1; done` → 3 chunk 分时到达（+6/+1005/+2006ms，spread 2000ms，非批量）✓
- domain tsc 0 + 49/49；web tsc 0 + 81/81
