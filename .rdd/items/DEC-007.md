# DEC-007: web/interface 架构范式 = 静态 SPA(Vite) + hono node sidecar（UI/后端解耦，桌面端复用）

## 问题
web 现状用 Next.js 把 UI（presentation）与 API 路由（driving adapter）耦在一个包，`.next/standalone` 在 local-first 工具上系统性不适配（Windows pnpm junction EPERM、ripgrep 不被 trace、不用 standalone 就 ~1.2GB）。未来桌面端（Electron）要复用什么形态？

## 决策
- web/interface 采用 **静态 SPA（Vite 构建 `dist/`）+ 独立 hono node server（sidecar）** 范式。UI 与后端解耦。
- server（hono）= 薄 HTTP driving adapter，只依赖 `@any-code/domain`，无业务逻辑；web SPA 经 HTTP 契约驱动应用。
- 桌面端（后续特性）复用此范式：Electron `loadFile` 静态 `dist/` + spawn hono sidecar（或内嵌）。

## 理由
- UI 全 `"use client"`（Next 的 SSR 价值零提取）——换静态 SPA，SSR 零损失。
- 静态 `dist/` 无 node_modules / 无 pnpm junction → Windows EPERM **结构上根除**。
- server 解耦 → 运行时不依赖 Next standalone tracing（ripgrep 等 vendor 机制不变即可，无新坑）。
- 对齐 opencode（同用 hono + sidecar）/ hermes（Vite SPA + Python server）。
- 桌面端直接复用 server 包 + 静态 dist，是"打基础"的最小路径。

## 影响的跨特性范围
- FE-019（web 重构）、未来 Electron 桌面端特性、未来 tui（已有独立 in-process driving adapter，不冲突）。
