# Raw Requirement: write 工具端到端重构优化（解决大写入卡顿）

## 来源
用户：write 写入量特别大时 web 端像卡死。调研业界主流 agent harness 的写入工具，全面端到端重构优化 anycode write。

## 根因（三重）
1. **LLM 流式 tool_call.arguments 期间事件流静默**（主因）：streamCall 累积 delta.tool_calls[].function.arguments（文件 content）但不发事件（只 content delta 发 ASSISTANT_DELTA）→ 大 content 流式期间 SSE 静默 → web 卡死。同 bash 卡顿根因。
2. **TOOL 事件 data.args.content 携带全文**：toolCall.ts 的 data:{name,args,result}，args 含 content 全文 → SSE 大 payload + 前端 parse 大 JSON 卡。
3. write 非原子写（半写风险）。

## 调研结论（业界主流 agent harness，按路线归纳）
- **路线 A（CLI agent 闭源）**：write 整文件覆盖，无 content cap。
- **路线 B（本地 agent）**：stdin 管道原子写（无 ARG_MAX）；patch/str_replace 优先减量；result 事件一传输路径不带 content（摘要+diff），另一路径带（同 anycode bug）；流式 arguments 静默未解决（只发 started 转圈，自承"避免冻屏"）。
- **路线 C（插件化 harness）**：流式 arguments 每 chunk 发事件非静默（但 tool 卡片等 assembled 才渲染）；result 短信封 + hunk diff meta；edit 工具源头减量；原子写 temp+rename；前端折叠+虚拟化。

## 可借鉴点（按性价比）
1. 流式 arguments 心跳（路线 C 非静默；路线 B 未解决）
2. TOOL 事件不带全文 args（路线 B ACP 路径 + 路线 C hunk diff）
3. 原子写 temp+rename（路线 B/C）
4. edit/patch 优先减量（路线 B/C，anycode 已有 edit 工具，强化引导）
5. staleness 校验（路线 B：read 记 mtime，write 前对比警告）

## 范围
- domain：streamCall 加流式 arguments 心跳；toolCall TOOL 事件 args 截断；write 原子写；staleness 校验
- web：收到心跳显"正在生成写入… N bytes"指示器；TOOL 事件 args 已截断不渲染全文
- system prompt：强化 edit 优先引导

## 未定（见 Open Questions）
- 流式 arguments 心跳形式
- TOOL 事件 args 截断策略
- 原子写 / staleness 范围

## 决策（Human 决）
- 心跳 = 发 TOOL_ARG_PROGRESS 事件（每 2KB，只 bytes+name，DEC-076）
- TOOL args content 截断（>500，DEC-077）
- 原子写 + staleness + edit 引导 全做（DEC-078/079/080）
