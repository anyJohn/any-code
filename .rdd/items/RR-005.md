# Raw Requirement: 核心路径单测

## 来源
- README Roadmap P0-3
- 现状：三个包测试 0%，仅 TUI 做 prettier 格式检查；每次重构（RR-001/RR-002 已多次动 domain）靠手测，无回归网

## 业务目标
- 给关键路径加单测，让后续 P0（RR-003 MCP / RR-004 流式）与 P1 重构有回归网
- 不求高覆盖，求"动哪里就先有那里的测试"——渐进式补建

## 范围
关键路径（优先级从高到低）：
- **domain/src/core.ts** `agentLoop`：有 tool_calls→执行→回灌→循环；无 tool_calls→返回；abort→stopped；达 maxIter
- **domain/src/tools/toolCall.ts**：按 function name 派发、TOOL 事件提交、未知工具处理
- **domain/src/main.ts** `executeTask` / `initProcessor`：task$ 串行（concatMap）、stop$ 中断、pendingTasks$ 更新、session 延迟创建
- **domain/src/session/**：append/load/findKey/findSession、entries↔session 转换
- **domain/src/eventStream.ts**：submit→event$/history$、per-agent 隔离
- 可选：web `parseSSE`（纯函数，易测）

## 未确定事项（待逐个收敛 spec）
- **测试框架**：vitest（ESM 友好、与 esbuild/turbo 贴合）vs jest？domain 是纯 ESM，vitest 更顺
- **覆盖率目标**：不设硬指标，原则"改哪里先补哪里"
- **mock 策略**：mock LLM（返回固定 tool_calls/content）以测 agentLoop 控制流；mock 文件系统以测 session store
- **LLM 行为依赖边界**：agentLoop 的控制流（有/无 tool_calls、abort、maxIter）是纯代码路径，mock LLM 可证；非"LLM 真会调某工具"的行为依赖（那类要真 LLM run，见 rdd Verification 节），本 RR 不覆盖
- **测试基建**：domain package.json 加 test script + 测试依赖；是否纳入 `pnpm test`（根 `-r test`）

## 场景判断
**场景 A（增量改进）**：纯加测试，不改产品行为；既有代码无 Spec，按 rdd 渐进式 Spec 覆盖——接触 core.ts/toolCall.ts 时补 inferred Spec，测试即 Spec 的 AC 落地。
